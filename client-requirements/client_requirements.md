# Implementation of Real-Time Operational Intelligence Platform

## 1. Business Background
The client operates across multiple regions (EU, US, APAC) relying on disparate systems (ERP, CRM, OMS) to manage critical business workflows. Currently, the organization faces challenges in tracking end-to-end process visibility. There is no centralized, real-time mechanism to monitor process lifecycle statuses ("Intake" to "Completion"), resulting in undetected failures and an inability to identify long-running processes.

## 2. Business Objectives
- **Real-Time Monitoring:** Track operational events as they happen to minimize reaction time to critical failures.
- **Bottleneck Identification:** Identify specific process stages or Source Systems (e.g., CRM vs. ERP) that are causing delays.
- **SLA Enforcement:** Automated tracking of "Long Running" processes (defined as > 300 seconds).
- **Regional Performance:** Compare processing efficiency and error rates across EU, US, and APAC regions.

## 3. Functional Requirements

### 3.1 Data Sources
- **Real-time Stream:** Ingestion of operational event logs via Azure Event Hubs from multiple source systems including ERP, CRM, OMS, and monitoring tools.
- **Event Attributes:** Tracking of `event_id`, `process_id`, `process_stage`, `event_status`, `priority` (Low to Critical), `source_system`, `region`, `event_start_time`, `event_end_time`, and `processing_time_sec`.

### 3.2 Data Processing & Storage
- **Medallion Architecture:** Implementation of a Lakehouse architecture on Azure Data Lake Storage (ADLS) Gen2:
  - **Bronze:** Raw JSON ingestion from Event Hubs.
  - **Silver:** Parsed, cleaned, and schema-enforced data.
  - **Gold:** Star Schema modeling for analytics.
- **Schema Evolution:** The Silver layer must automatically handle schema drifts (e.g., new columns added by source systems) using `mergeSchema` options.
- **Dimensional Modeling:**
  - **SCD Type 2 (Slowly Changing Dimensions):** Implemented for the `dim_process` table to track changes in Process Priority and Stage over time, utilizing hash comparison (`_hash` vs `_target_hash`) to detect changes.
  - **Simple Dimensions:** Deduplicated dimensions for Regions and Source Systems.
  - **Star Schema:** A central `fact_operational_events` table linked to dimensions via surrogate keys.

### 3.3 Analytics & Reporting
- **Azure Synapse Analytics:** Serverless SQL pool to expose Gold tables as external tables (`ParquetFileFormat`) for downstream BI tools.
- **Power BI KPIs:**
  - **Success Rate:** Ratio of `is_success` (Completed events) vs. total events.
  - **SLA Breaches:** Count of `is_long_running` events (processing time > 300s).
  - **Average Processing Time:** Aggregated by Region and Source System.
  - **Failure Analysis:** Top failing processes by Priority.

### 3.4 Orchestration & Automation
- **Streaming Ingestion:** Continuous execution using Spark Structured Streaming with checkpointing for fault tolerance across Bronze and Silver layers.
- **Gold Orchestration:** The Gold layer is orchestrated via Azure Data Factory, triggering batch transformations every 5 minutes when 5 or more new records are detected in Silver. This approach enables near real-time availability while preserving SCD Type 2 correctness, which requires full access to historical dimension data.
- **Failure Alerting:** Azure Monitor alert rules notify the pipeline owner by email within 1 minute of any pipeline failure.
- **Incremental Loads:** Gold layer transformations must use Delta Lake `MERGE` operations to handle updates and prevent duplicates.

### 3.5 Data Quality & Validation
- **Dirty Data Handling:** The pipeline must robustly handle simulated data issues generated by source systems, including:
  - **Future Timestamps:** Correcting `event_start_time` that is in the future (5% probability).
  - **Negative Durations:** Recalculating `processing_time_sec` if negative values are received.
  - **Missing End Times:** Handling `NULL event_end_time` by defaulting to current timestamps or derived values.

### 3.6 Security
- **Secret Management:** All connection strings and access keys are stored in Azure Key Vault and accessed via scoped references from Databricks and Data Factory — no credentials are exposed in code.
- **Access Control:** Use of Azure Managed Identities for Synapse to access ADLS. Least-privilege role assignments apply: Databricks and Data Factory are granted Key Vault Secrets User only.
- **Network Security:** `SASL_SSL` protocol for Kafka/Event Hub communication.

## 4. Deliverables
- **End-to-End Pipeline:** Python/Spark scripts for Bronze, Silver, and Gold transformations.
- **Data Warehouse:** Synapse SQL scripts defining External Tables and Views.
- **Data Generator:** A Python script to simulate real-time load and dirty data injection for stress testing.
- **Orchestration Pipeline:** Azure Data Factory pipeline with conditional trigger logic and failure alerting.
- **Git Repository:** Full project repository organized into `databricks-notebooks/`, `data_generator/`, and `sqlpool-queries/` — credentials removed.

## 5. Success Criteria
- **Data Accuracy:** Accurate handling of SCD Type 2 history for process priorities.
- **Resilience:** Pipeline continues to function without failure even when receiving invalid timestamps or negative integers.
- **Latency:** Data available for analysis in the Gold layer within 5 minutes of event generation under normal operating conditions.
